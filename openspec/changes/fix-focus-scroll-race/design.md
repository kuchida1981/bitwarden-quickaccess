## Context

`app/dist/app.js` の検索結果一覧は、矢印キーによるフォーカス移動時に `updateFocusRows()` が対象行を差分更新し、`scrollIntoView({ block: "nearest" })` で表示範囲外の行をスクロールして見せる。同様の呼び出しは `renderResults()` 内にもある。

各行には `mouseenter` リスナーが付いており、マウスカーソルが乗った行に `focusedIndex` を切り替える。これはマウスホバーで行を選択できるようにするための意図した挙動で、行の境界を実際に跨いだ時にしか発火しない(同じ行の中でカーソルが微小に動いても再発火しない)という性質を持つ。

問題は、`scrollIntoView` によるスクロールでレイアウトが変わると、マウスカーソルは物理的に動いていないのにカーソル直下の要素が変わり、ブラウザが新しく直下に来た行の `mouseenter` を発火させてしまうこと。これにより `focusedIndex` がキー操作した行からマウスカーソル下の行へ意図せず上書きされる(#128)。

## Goals / Non-Goals

**Goals:**
- プログラム的スクロール(`scrollIntoView`)に起因する誤ったフォーカス変更でフォーカスが奪われないようにする
- マウスの実際の移動によるホバーフォーカス切り替え(意図した挙動)は維持する
- 実際には静止していないマウス(トラックパッド上の指の微小な震え等による1px程度のジッター)が、キー操作で移動させたフォーカスを同じ行の中で繰り返し奪わないようにする
- 特定のタイミング(WKWebViewのレンダリングサイクル、イベント発火順序)に依存しない、原理的に確実な方式にする

**Non-Goals:**
- action メニューまわりなど、本changeのスコープ外のイベント委譲アーキテクチャの見直し(#91で別途検討)
- 一覧のDOM構築・差分更新方式(既存の行再利用ロジック)の変更

## Decisions

- **採用方式: per-row `mouseenter` は維持しつつ、発火時の座標を「直近の本物の `mousemove` 座標」と比較して、進入が本物の移動によるものか、レイアウト変更による亡霊イベントかを判定する。** `resultsList` に `mousemove` リスナーを追加し、発火のたびに `lastRealMouseX`/`lastRealMouseY` を更新する(このリスナー自体はフォーカス変更を行わない)。各行の `mouseenter` ハンドラは、発火時の `event.clientX`/`clientY` がこの直近座標と完全一致する場合は「カーソルは物理的に動いていない=亡霊イベント」と判断して無視する。一致しない場合は「本物の移動による進入」として `focusedIndex` を更新する。

  この方式が確実に機能する理由: `mousemove` はブラウザがプログラム的なスクロールやレイアウト変更から合成することはなく、実際にポインタが物理的に動いた場合にのみ発火する。カーソルが物理的に動いていなければ、`scrollIntoView` 起因の亡霊 `mouseenter` の座標は直近の本物の `mousemove` の座標と完全に一致する。逆に本物の移動による行への進入では、必ず新しい座標になる(でなければそもそも別の行の境界を跨げない)。この判定はイベントの発火順序(`mouseenter` と `mousemove` のどちらが先か)に一切依存しない、値の比較のみに基づく。

  `mouseenter` の「行の境界を跨いだ時にしか発火しない」という性質をそのまま活かせる点も重要で、これにより人間の手が実際には完全に静止できないことに由来する微小なジッター(小さな `mousemove` は発生するが、同じ行の中に留まる限り境界を跨がないので `mouseenter` 自体が再発火しない)の影響を受けない。

  検討し、却下した代替案(このchangeの実装過程で実際に試して問題が発覚したものを含む):
  - **タイマー方式**(issue内の案1: スクロール直後の一定時間 `mouseenter` を無視): 無視すべき時間がWKWebViewのレイアウト/ペイントサイクルのタイミングに依存し、環境によって不足・過剰のいずれかになり得るため脆い。
  - **「`mouseenter` を一時的に無視するフラグ」を `mousemove` で解除する方式**(1回目に実装したが誤りと判明): `scrollIntoView` 呼び出し直前にフラグを立て、`resultsList` 上で実際に `mousemove` が発生した時にフラグを解除する案。コードレビューで指摘されて判明: ブラウザの標準的なイベント順序では、カーソルが新しい要素に入る際 `mouseenter`/`mouseover` は同じ入力サンプルの `mousemove` より**先**に発火する(逆ではない)。そのため、キー操作によるスクロール直後に実際にマウスを別の行へ動かした場合、その最初の `mouseenter` はフラグがまだ立ったままで無視されてしまい、ホバー切り替えが機能しなくなる回帰を生んだ。
  - **同フラグを `requestAnimationFrame` で解除する方式**(2回目に実装したが、これも誤りと判明): スクロール起因の亡霊 `mouseenter` は次の `requestAnimationFrame` コールバックより前に発火する、という前提を置いたが、これはWKWebView上で実際には成立せず、ユーザーによる動作確認で元の不具合(#128)の再現が報告された。
  - **per-row `mouseenter` を廃止し、`resultsList` への `mousemove` イベント委譲(`event.target.closest("li")` でホバー行を特定)に完全に置き換える方式**(3回目に実装したが、これも誤りと判明): `scrollIntoView` が全く発生しない状況でもユーザーの動作確認で不具合が再現した。原因は、`mousemove` は行の境界を跨がなくても(同じ行の中の微小なジッターでも)発火するため、`focusedIndex` がキー操作で別の行に移った後、カーソルが乗ったままの行で発生するどんな小さな `mousemove` でもフォーカスが即座にその行へ引き戻されてしまうこと。`mouseenter` の「境界を跨いだ時にしか発火しない」という性質を手放したことが根本原因だった。
  - 上記2つの反省(タイミング依存のフラグは信頼できない/`mouseenter`の境界跨ぎ性質は手放せない)を踏まえ、`mouseenter` を判定のトリガーとして維持しつつ、判定基準を「タイミング」から「座標の一致比較」に置き換える今回の方式に至った。

- **座標の保持スコープ**: `lastRealMouseX`/`lastRealMouseY` はモジュールスコープの変数とする(既存の `focusedIndex` 等と同様のスタイル)。

## Risks / Trade-offs

- [Risk] ポップアップが開いた直後、一度も `mousemove` が発火する前(`lastRealMouseX`/`Y` が `null` のまま)にカーソルがすでに一覧上のある行に乗っている状態で、その行に対して最初に発火する `mouseenter` があった場合、`null` とは一致しないため「本物の進入」として扱われる → [Mitigation] 実用上、ユーザーがカーソルをその行まで移動させる過程で必ず `mousemove` が先に発火するため、この状況(一度も `mousemove` を経ずに `mouseenter` だけが発火する)は現実的にはほぼ起こらない。仮に起きても実害は「最初の1回だけ本来の(意図した)ホバー動作と同じ結果になる」程度。
- [Risk] `mousemove` は `mouseenter`/`mouseleave` より高頻度に発火するため、座標更新用リスナーの実行コストが増える → [Mitigation] リスナー内の処理は2つの数値代入のみで、無視できるコスト。
