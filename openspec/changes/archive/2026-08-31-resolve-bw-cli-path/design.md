## Context

`fix_path_env()`(`app/src-tauri/src/main.rs:98-112`)は `main()` の最初、`tauri::Builder` 構築前(tokioランタイム不在)で同期的に1回だけ呼ばれ、ログインシェルを spawn して `printenv PATH` の結果をプロセス全体の環境変数に `unsafe { std::env::set_var(...) }` で反映している。

調査の結果、このアプリでプロセス全体のPATHに依存しているのは実質 `Command::new("bw")`(`preflight.rs::check_bw_cli` のデフォルト引数、`process.rs::build_bw_serve_command`)の2箇所のみであることを確認済み(`sh` は常に `/bin/sh` を使用、「ブラウザで開く」は `tauri_plugin_opener` 経由でシェル外部コマンドに依存しない)。また `bitwarden-cli` は homebrew-core の正式formula(node依存)であり、手元環境でも `which bw` → `/opt/homebrew/bin/bw`、`npm config get prefix` → `/opt/homebrew` が確認できている。一方、Bitwarden公式のインストール手順にはnpmグローバルインストール(node管理ツール次第でパスが不定)とネイティブバイナリの手動配置(所在が完全に自由)も含まれており、これらは静的パス探索では原理的にカバーできない。詳細な経緯は proposal.md および Issue #109/#83、`openspec/changes/archive/2026-08-27-fix-path-env-thread-safety/design.md` を参照。

## Goals / Non-Goals

**Goals:**
- ログインシェルの spawn を完全に廃止し、`bw` 実行ファイルの所在をファイルシステム探索(既知パス)とユーザー指定(設定ファイル)のみで解決する
- `unsafe { std::env::set_var(...) }` によるプロセス全体のPATH書き換えを撤去する(解決済みパスをコマンドへ直接渡す)
- 解決ロジックを、既存の `check_bw_cli_with()` と同様のパターン(値を注入してユニットテスト可能)で実装する
- `bw` が見つからない場合のエラーメッセージに、ユーザーが取れる具体的な対処(設定ファイルの場所と書き方)を含める

**Non-Goals:**
- nvm/volta/asdf等のnode管理ツール経由でインストールされた `bw` を自動検出すること(設定ファイルによる明示指定が正式なサポート方法であり、自動検出は行わない)
- 設定ファイルを編集するGUI画面の提供(プレーンテキストファイルを手動編集する運用を前提とする)
- Linux版のビルド・配布(README記載通り現状Apple Silicon macOS onlyがスコープ。ただし設定ファイルの置き場所にXDG規約を採用するのは、将来Linux対応する際の親和性を考慮した設計判断であり、Linux固有の既知パス追加は本changeでは行わない)
- タイムアウト値・ポーリング間隔など、廃止対象コードに残っていたパラメータの調整(コード自体を削除するため無関係)

## Decisions

### 1. 既知パスは `/opt/homebrew/bin/bw` → `/usr/local/bin/bw` の2つに限定する

**採用理由**: `bitwarden-cli` homebrew formulaはnode依存で `brew --prefix` 配下にインストールされる。Apple Silicon(`/opt/homebrew`)・Intel/Rosetta(`/usr/local`)のいずれも、Homebrew由来のnodeで `npm install -g @bitwarden/cli` した場合も同じ場所に着地するため、この2パスでHomebrew経由インストールとnodejs.org公式インストーラ経由のnpmグローバルインストール(prefixが慣習的に `/usr/local` になりやすい)の大部分をカバーできる。

**却下した代替案**:
- `npm config get prefix` を実行時に呼んで動的にprefixを取得する: サブプロセスをspawnして待つ必要があり、今回廃止したい「シェルspawnによる待機」という設計そのものを部分的に復活させてしまう。またnvm等バージョン管理下のnodeには結局対応できない(現在アクティブなnodeバージョンのprefixしか分からず、GUIアプリ起動時のシェル外環境ではそもそも「アクティブなバージョン」という概念が存在しない)ため、複雑さに見合う効果が薄い。
- `$HOME` 配下のnvm/volta/asdf等の既知ディレクトリ構成を推測してスキャンする: バージョンディレクトリを列挙するロジックが必要になり、ツールごとの構成差異(nvmは`versions/node/vX.Y.Z/bin`、voltaは`bin`直下等)に追従し続けるコストが高い。ユーザーに明示してもらう設定ファイルの方が単純で確実。

### 2. 設定ファイルはプレーンテキスト、XDG準拠のパスに配置する

`$XDG_CONFIG_HOME/bw-quickaccess/bw_path.txt`(`XDG_CONFIG_HOME` 未設定時は `~/.config/bw-quickaccess/bw_path.txt`)に、`bw` 実行ファイルの絶対パスを1行だけ書く形式とする。

**採用理由**: このアプリはこれまで永続的な設定・データファイルを一切書いておらず、踏襲すべき既存の慣習が存在しない。この機能の主な対象ユーザー(nvm等でnodeを管理している開発者)はXDG系のパスに慣れており、`~/Library/Application Support/...` より発見・編集しやすい。将来Linux対応する際にもこのパスの考え方をそのまま流用できる。単一パスの読み書きのみなので、TOML/JSON等のパーサcrateを追加する必要がなく、`std::fs::read_to_string` + `trim()` で完結する。

**却下した代替案**:
- `~/Library/Application Support/<bundle-id>/`(Tauri `app.path().app_config_dir()`): macOS作法としては正統だが、このアプリは未署名・未notarize配布でApp Sandbox化の予定もなく、Tauri標準パスを使う技術的必然性は薄い。対象ユーザーにとって発見しにくい場所でもある。
- 環境変数のみ(例: `BW_QUICKACCESS_BW_PATH`): Finder起動・ログイン項目起動ではシェルrcで設定した環境変数がアプリに継承されず、ユーザーが別途 `launchctl setenv` する必要がある。これは今回解決したい「GUI起動時にPATHが伝わらない」問題と同種の壁にぶつかるため、ファイルより優れているとは言えない。
- TOML設定ファイル: 現時点で永続化すべき設定項目が1つしかなく、パーサ導入は時期尚早。将来設定項目が増えた場合に改めて検討する。

### 3. 解決順序: 設定ファイル → 既知パス → 素の `"bw"`(PATHフォールバック)

ユーザーが明示した設定を最優先し、次に高確率でヒットする既知パスを試し、最後に「たまたま現在のプロセスのPATHに `bw` が含まれている」ケース(ターミナルから `cargo run` する開発時、あるいは他の要因でPATHが十分な場合)を拾う。設定ファイルのパスが存在しても実行可能ファイルとして無効(削除済み・パス誤り等)な場合は、エラーにせず次の既知パス探索にフォールスルーする(壊れた設定ファイルでアプリが起動不能になることを避ける)。

### 4. 解決処理を `start_backend()`(非同期、`app_handle` あり)に移す

`fix_path_env()` が `main()` 起動前の同期処理に置かれていたのは、当時「プロセス全体のPATHをtauri起動前に書き換えておく必要がある」という制約があったため(#83のdesign.mdでも明記)。今回、プロセス全体の環境変数を書き換えず、解決したパスを呼び出し箇所へ値として渡す設計に変えるため、この制約自体が不要になる。ファイルシステムI/Oは `start_backend()` 内(`preflight::check_bw_cli()` 呼び出し直前)で行う、通常の非同期処理として実装する。

### 5. `unsafe` の撤去: 値渡しへの変更

`preflight::check_bw_cli_with(bw_path: &str)` は既にパスを引数で受け取れる形になっているため、デフォルト用の `check_bw_cli()` の中身を `"bw"` 固定から解決済みパスに差し替える(あるいは呼び出し元で直接 `check_bw_cli_with(&resolved_path)` を呼ぶ)。`process::build_bw_serve_command(port: u16)` は `bw_path: &str` を追加引数に取るよう変更し、`Command::new(bw_path)` とする。これにより `main.rs` から `fix_path_env` / `PATH_MARKER` / `run_shell_and_capture_stdout` と関連テストを丸ごと削除できる。

新しい解決ロジック自体は `app/src-tauri/src/backend/` 配下に新規モジュール(例: `bw_locate.rs`)として切り出し、`check_bw_cli_with` と同じ思想で「候補パスのリスト」「設定ファイルのパス」を引数として注入できる形にし、実ファイルシステムを使った軽量なユニットテスト(一時ディレクトリに空ファイルを置く等)で検証可能にする。

## Risks / Trade-offs

- **[Risk] nvm/volta/asdf経由や手動配置の `bw` を使っているユーザーは、設定ファイルを作成するまで「バックエンド未接続」エラーになる** → 現行の `fix_path_env()`(ログインシェル起動)では動いていたケースが、今回の変更で退行しうる唯一のシナリオ。エラーメッセージに設定ファイルの場所・書き方を明記し、READMEにも手順を追記することで対処する。この変更をリリースする際は、リリースノートでもこの挙動変化に触れることが望ましい(tasks.mdでは明示のタスクにはしないが、リリース時に留意する)。
- **[Risk] 設定ファイルが存在しても中身が不正(空・存在しないパス等)な場合に無限にフォールスルーする** → 前述の通り既知パス探索・PATHフォールバックへ自然に落ちるため、アプリが起動不能になることはない。最終的にどこにも見つからなければ通常の「CLI未検出」エラーになる。
- **[Risk] 将来Homebrewのインストール先の慣習が変わった場合、既知パスリストが陳腐化する** → 発生確率は低く(Homebrewのprefix規約は長年安定)、その場合も設定ファイルが救済策として機能する。
- **[Trade-off] 今回の変更で「プロセス全体のPATH」を直す仕組みが完全に無くなる** → 現状PATHに依存する外部コマンド呼び出しは `bw` のみと確認済みだが、将来別の外部コマンドを素のコマンド名で呼び出す機能を追加する場合は、今回撤去したPATH全体修正の恩恵を受けられない点に注意が必要(その時点で個別に絶対パス解決するか、改めてPATH全体の扱いを検討することになる)。

## Migration Plan

内部実装のみの変更であり、外部インターフェース・データ形式の破壊的変更はない。設定ファイルは新規導入だが、存在しない場合は既知パス→PATHフォールバックへ進むだけなので、既存ユーザー(Homebrew経由が大多数と推測される)は無変更で動作し続ける想定。上記Risksに記載の通り、Homebrew以外のインストール方法を使っている一部ユーザーには挙動変化(設定ファイル作成が必要になる)があるため、リリースノートでの周知を推奨する。ロールバックは通常のリバートで対応可能。

macOS実機での動作確認(Homebrewでインストールした `bw` での通常起動、既知パスにない場所に `bw` を置いた状態で設定ファイル経由の起動、設定ファイルもPATHも無い状態でのエラーメッセージ確認)をリリース前の確認事項とする(tasks.mdに手順を記載)。
